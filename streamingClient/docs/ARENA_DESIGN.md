# 观众生存世界：设计与 SVG 混战原型

2026-10-18。用户确认：混战与共同打怪都要，先做玩家自动混战。当前保留为独立的 SVG 玩法原型源码，尚未接入工作台场景插件。猪大 VS 恶龙方形静态插件仍随客户端内附。

## 已确认方向

- 观众赠送指定入场礼物（拟用人气票）加入，生成带本人名称的角色。
- 已入场玩家赠送任意礼物，为自己的角色增加属性。拟用一个一毛礼物随机增加一点属性；实际 giftId、价值及映射须从工作台目录配置，不能按显示名称硬编码。
- 力量影响攻击力，敏捷影响攻击速度，最大生命决定血量上限。
- 默认镜头跟随存活最久的当前玩家。小心心抢镜两秒；下一笔覆盖上一笔，重新计时，不排队。
- 大地图、角色与特效全部使用 SVG；世界为 2D。左侧显示可滚动的玩家状态，游戏地图为方形，未来作为可缩放图层插入直播场景，约占直播画面的三分之一。

真实礼物分发有自动化夹具覆盖，尚无本次公开源码整理期间观察到真实人气票生成角色的验证记录。连接成功不能作为这一功能已通过真实直播验收的证据。

## 原型现在可以做什么

原型源码和单元测试仍保留，方便后续以正式插件形式接入。当前客户端不启动它的独立预览服务，也不会把它当成已完成的直播功能；正式接入前仍需完成场景来源声明、全局事件映射、手机预览和 Windows 实机验收。

真实份数当前仍是试玩数值：每份新增礼物随机加 1 点，不按钻石价格折算；入场、抢镜也只执行一次加点。单笔新增量超过 1000 份或本轮超过 50000 个事件会明确拒绝，不静默截断。正式付费数值、存档、全局热键和场景插件分发尚需后续完善。

2560 × 2560 SVG 世界包含草地、石板广场、路径、村屋、树林、具名角色、血条、近战动作、伤害与加点提示、小地图。镜头追踪榜首，抢镜期间平滑转向新玩家。左侧榜单能滚动，更新时保持滚动位置。角色使用共享 SVG symbol；仅创建当前镜头附近的角色节点，不逐帧重建整张 SVG。

世界只在一个宿主进程运行，以 100 毫秒固定步长计算，浏览器通过 SSE 接收同一状态并插值显示。模拟试玩使用 Node 进程，真实模式使用 Electron 主进程。多个预览不是多个独立对局。原型进程退出后清空，不代表已实现正式宿主持久化与手机二维码接入。

预置 24 个模拟玩家，可新建玩家、模拟三类礼物、批量增加 8 人、暂停或重置。64 人为原型同时存活上限。模拟量是属性点单位，没有对应真实礼物价值；入场和抢镜礼物也同时提供相应份数的随机加点。

## 原型采用的临时规则

这些默认仅为试玩，不代表用户已确认正式数值。

- 每位玩家同一时间只有一个活角色，以稳定用户 ID 识别，不能用昵称当唯一键。活着时重复入场不创建分身；阵亡后入场创建新生命并重置属性与生存时间。
- 基础力量 18、敏捷 0、最大生命 1000。每份模拟礼物随机且等概率增加一点力量、敏捷或最大生命。增加最大生命同时回复这新增的一点，不额外满血。
- 属性持续到本次角色阵亡，不沿用旧双阵营游戏“每轮清零”的设计。存活 30 秒记为一轮，按个人出生后完整存活时间累计，不能刚好赶上全局结算线就白拿一轮。
- 存活时间最长者优先，同时间按击败数与稳定 ID 排序。击败归属为本次致命 tick 伤害最高的攻击者；同伤害按稳定 ID 决定。该规则后续可以替换。
- 出生保护 2.5 秒，保护期间双方都不能对其造成伤害或利用保护攻击别人。角色自动接近最近的可攻击对手，再近战攻击。
- 每击伤害等于力量；攻速为 `1 + 2 × 敏捷 / (敏捷 + 40)` 次/秒，上限趋近每秒 3 次，避免线性堆叠到无限攻速。
- 同一逻辑 tick 的攻击同时结算，允许同归于尽，不因玩家遍历顺序吞掉攻击。停止时钟也停止战斗、出生保护和两秒抢镜。
- 抢镜目标阵亡立即恢复榜首镜头；未入场或已阵亡玩家的小心心不会凭空创建角色，测试面板明确拒绝该操作。正式版应在直播说明中事先清楚展示入场前提。
- 原型事件使用唯一 ID 去重。正式礼物连击必须接工作台已确认的数量增量，不能每次收到累计数都重复加点。重复事件不加点也不延长抢镜。

## 正式设计需要解决的问题

### 生存目标与人数

只有一个玩家时不会自行战斗；其他玩家全部阵亡后也会等待新玩家。正式版需确定等待阶段、开战人数及单局终点，并决定是否用中立怪物、缩圈或限时赛事解决独苗与躲藏问题。共同打怪模式可以复用地图、角色、礼物归属和镜头系统，但其刷怪、波次与结算尚未实现。

### 新老玩家差距

如果永久保留属性又持续用存活榜首占镜头，会形成老玩家资源与曝光双重优势。建议正式首版采用有终点的赛事，或分区保护与匹配；应先选定规则再做付费数值。原型的出生保护仅解决刚生成就被打死，不保证新老玩家公平。

### 一点属性不等价

当前 +1 力量、+1 敏捷、+1 最大生命的实际收益不相同，原型故意保持用户提出的原始规则供比较。正式版建议引入统一成长点，再各自换算伤害、攻速、生命的增幅，或为三项设置不同增量；不能仅因都写“+1”就认为等价。随机结果由唯一宿主生成并保存，渲染器不能自行随机。

### 所有礼物与特殊礼物的叠加

建议一笔礼物先处理入场或抢镜，再执行一次通用加点；特殊礼物不应走两次加点路径。需要确定未入场玩家普通礼物的处理、重复入场是否有额外作用、死亡后的礼物归属、实际礼物价值折算、每件还是每批随机。原型暂采用逐份独立随机，入场/抢镜也加点，未入场普通礼物明确拒绝，不承诺已存入未来角色。

### 抢镜风暴

明确采用最新有效礼物覆盖、从接受时刻重新计时两秒；不排队，不让旧定时器切回旧角色。应限制镜头缩放和移动速度，避免快速连续送礼导致闪屏。实际礼物按工作台接受顺序处理；重复、模糊增量和其他房间的礼物不能抢镜。没有采用抢镜冷却去改变用户提出的覆盖规则。

### 手机可读性与世界规模

地图大与直播视窗大是两件事，镜头只显示附近区域，小地图展示全局。在三分之一直播画面内不可能同时看清几十人的全部属性，应优先突出镜头目标，左侧列表滚动查其他人。未来状态列表、角色详情与地图应为同一运行实例的独立展示来源，方便主播摆放与缩放。

SVG 适合首版 2D 风格，但不能承诺无限人数不卡。原型使用全量人数受限的最近目标搜索；正式扩容应采用空间分区寻敌、地形碰撞与视口裁剪，并在 Windows、Mac 和手机做实际性能验收。当前村屋、树石是美术装饰，尚无寻路障碍；正式地图不能把装饰当作已经实现的地形系统。

### 玩家操作与长期目标

礼物入场、具名角色、存活成绩与抢镜已经建立个人归属。下一步还需试玩验证：自动寻敌是否有看点，观众是否需要“追击／撤退”等少量指令，以及死亡重入是否有明确目标。身份、战报与纪录可以保留，付费战斗增益的跨局继承须另行确定，不能默认永久滚雪球。

## 接回工作台前的接口工作

现有 `SceneEvent` 已能提供 senderId、senderName、giftId、去重后的 quantity；现有通用变量是图层级数值，不能直接当作多人角色数据库。

正式接入应增加按插件运行实例隔离的宿主世界状态、版本化配置和存档、完整的礼物归属/增量处理、读状态展示接口。共享同一实例的地图、榜单、手机预览只消费同一权威状态。不能把这个原型引擎分别放进每个 iframe，让每个预览各跑自己的战斗。

现有工作台的房间隔离、热键和全局测试入口继续复用；任何礼物不能仅凭匿名手动触发就猜测赠送者。需要为试送指定模拟玩家，为热键配置明确目标。新玩法完成以上工作后，才作为有版本号、可独立更新的本机插件发布。
